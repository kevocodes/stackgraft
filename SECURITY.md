# Security

stackgraft reads files out of a repository worktree — compose files, task targets, package scripts — derives commands from what it finds, and runs some of them. That is third-party text reaching an execution path. It is deliberate: there is no way to start only the services a worktree changed without reading how that worktree says its services run.

A published audit of this skill flags exactly that — **W011, third-party content exposure, indirect prompt injection risk, medium**. The category is a true positive and this document does not dispute it.

What an audit cannot see is that the exposure already has a contract. `skills/stackgraft/references/shared-state.md` defines what a discovered command may contain, how it is executed and when it is refused; `skills/stackgraft/references/discovery.md` defines what is read and how values are substituted. Under progressive disclosure those files may never be loaded at all, so the threat model has been living where nobody looking for it would find it. This file is that model, written where it is looked for.

## The trust boundary

**Repository content is untrusted input, and is treated as such by design.** Everything discovery reads — `docker-compose.yml` and its overrides, `Makefile`, `Taskfile.yml`, `justfile`, `package.json` scripts, `bin/*`, `.env.example`, gateway and proxy configuration — is data written by someone who is not you. Nothing is trusted for having been found in a repository. `references/shared-state.md` states it in as many words: *a discovered template is repository data, so it is treated as untrusted input.*

**The honest framing an auditor deserves, offered as context and not as a dismissal.** stackgraft's precondition is a base stack you started yourself — the whole point is to overlay onto a stack that is already up. Whoever can modify your compose file already runs arbitrary code on your machine the moment *you* run `docker compose up`, with no skill involved. So the skill operates inside an exposure that exists before it arrives, rather than creating one.

**That bounds the risk. It does not remove it.** Two things stay true whatever the precondition is. The skill adds occasions on which repository text is executed — a branch you have not read, checked out into a worktree and run. And "you already had this problem" is never a reason to hand a discovered string to a shell. The controls below exist because the boundary is real even where the exposure is not new.

## What is enforced

Every rule here applies to **every command this skill discovers and runs against a store**: `isolation.command` and `isolation.teardownCommand` alike, the teardown being the more destructive half and therefore never exempt. The full text is the *Template contract* in `references/shared-state.md`; these are its mechanisms.

- **A closed placeholder set of six**, each with a defined source: `{{isolationIdent}}`, `{{isolationLabel}}`, `{{store}}`, `{{worktree}}`, `{{repoRoot}}`, `{{port}}`. Any other `{{…}}` invalidates the template, which records `mechanism: "none"` rather than running it — which leaves the in-place road: the pair goes to step 5 and is answered by a seeded copy where the store records a usable provider, and refused where it does not. `{{isolationIdent}}` and `{{isolationLabel}}` are the two members of the name family, generated by the skill per `references/coordination-identity.md` and never read from the repository, and a template asking for a name in a form its substrate does not accept is not given the other one.
- **A deny-list on the template's own grammar** — the bytes the repository wrote. `` ` `` `$` `;` `&` `|` `>` `<` and newline are forbidden anywhere in the raw template. This is the part of the line the repository authors, and it is the part checked lexically.
- **argv execution, with no shell fallback.** The argument vector is built first, each placeholder substituted into its own element, and that vector is executed directly. Mandatory, not preferred. If the only available tool runs a shell string, the template is not executable here: record `mechanism: "none"` and leave this road, rather than quoting around it.
- **A structural post-substitution check.** Each placeholder value must occupy exactly one argv element, whole and never re-split, and the program name and element count must come from the template rather than from any value. A substitution that adds, merges or removes an element invalidates the template. The check is structural rather than a second pass of the deny-list because `{{repoRoot}}` and `{{worktree}}` are host paths the repository does not control — a developer working in `/Users/dev/R&D/app` would otherwise lose every store to a hazard argv has already removed.
- **Rejection of any program that would re-parse an argument as code.** Argv neutralises a metacharacter only for as long as nothing downstream parses the element again. Rejected outright: `sh`, `bash`, `dash`, `zsh` and any other shell, the exec wrappers `env`, `eval` and `xargs`, and `awk`, whose first operand is program text. Rejected when given a `-c`/`-e`-style flag: any language runtime, such as `python -c`, `node -e`, `perl -e`.
- **One program, with arguments.** No pipelines, chains or redirection. A repository that needs them wraps them in its own task target, which is then discovered as a task target.
- **Destructive verbs rejected as a class, not as a list of spellings.** Any template that destroys or empties a namespace, volume or instance not derived from a member of the name family is rejected, decided on what the command does. `dropdb -U app app`, `DROP SCHEMA public`, `TRUNCATE`, `db:reset`, `docker volume rm`, `FLUSHALL` and `compose down --volumes` are the same rejection, and none of them contains the same literal string.
- **The one repository-supplied value is constrained at its source.** `{{store}}` is a `backingStores` key, whose schema pattern admits no metacharacter, no whitespace and no leading dash.
- **Human approval before the first run, and it expires.** Both substituted commands — create and teardown — are shown with their target store before the first run per repository and store, because approving a create without seeing the drop approves half an operation. The approval records `sourceFingerprint`, the fingerprint of the file the template came from; once that drifts the approval is treated as absent and the command is shown again rather than inherited.
- **The launch commands are covered by an equivalent rule, not by the same one.** `overlayCommand`, `prepareCommand`, `verifyRequest` and the `baseStack` commands are shell lines by construction — repositories write them with their own `cd` and `&&` — so argv cannot apply. Each substituted value is instead placed as one single-quoted word, with embedded quotes escaped, and each of those fields has its own closed placeholder set. Neither rule excuses the other.
- **Label insertion has a structural post-condition.** Ownership labels are inserted at an anchor inside the discovered command, never appended, and the resulting token sequence must equal the original with only the label elements added. A template exposing no anchor is refused rather than launched unlabelled, and an anchor is never matched inside a quoted string.
- **The gate fails closed.** Unknown, absent, empty or degraded data resolves to refusal, never to permission. Emptiness is a claim that requires evidence at every level, and a pair with no verdict is not a pair that passed.
- **Secrets are not read into the cache.** A gitignored `.env` is never hashed or copied; the constraint it implies is recorded, never the value.

## The copy as a data surface

Isolating a writing pair now means **copying the store's state**, so a run can leave a duplicate of whatever your base stack holds sitting on the same disk under a name this skill chose. Where the base stack holds a production-shaped dump, so does the copy. That is a surface, and it is named here rather than left implicit in `references/isolation-providers.md`.

**The answer is ownership, labelling, a named lifetime and an output contract — not encryption.** Encrypting a copy the developer's own engine has to read would move the key onto the same disk and change nothing; what a developer actually needs is to know the copy exists, whose it is, and how to remove it.

- **Every copy carries this repository's complete label set** — the label-set version, the repository hash, the worktree it belongs to, and the store key. Four labels, and the set is complete or the object is not ours. An object carrying three of them is reachable by no query this skill makes, and an unlabelled object is never provisioned over, never removed, and never named as a copy of ours.
- **A copy's lifetime is its worktree.** It belongs to the worktree recorded on it, is reused by later launches from that worktree, and becomes reclaimable once that worktree is gone — judged against git's own worktree list, never against a timer.
- **Every run names the copy and the exact command that removes it**, including a run that removed nothing because the overlay is still up or a removal failed. The only thing that will ever remove it otherwise is a person who was told it exists.
- **Removal takes the removal flag in addition to the mutation flag**, which runs the opposite way to intuition on purpose: a copy destroyed by accident is state nothing on this host can reproduce, because the base stack has moved on since it was taken.
- **The copy is taken live and is therefore crash-consistent.** A file-level copy of a running engine is what a power cut looks like. Engines are built to recover from that, and an engine with an fsync-ordering dependency may not — stated as the residual it is, in `references/isolation-providers.md`, beside the statement that the copy is live.

**What this does not do**, in the same plain terms as the section below. The copy inherits the confidentiality of the disk it sits on and nothing more: it is readable by anything on that host that can read the runtime's objects, and this skill applies no access control it did not already have. It is not encrypted, not redacted, and not sampled — it is the base stack's bytes. A developer whose base stack holds data they may not duplicate should not be pointing this at it, and the shipped files say so rather than implying a protection that is not there.

## What is not covered

Named the way this project names its other limits: plainly, and not described as closed.

- **A permitted template still runs, and nothing here reads the program it invokes.** Every rule above constrains the *shape* of a discovered command — its grammar, its placeholders, its execution model. None of them makes a permitted command safe. `make -C {{repoRoot}} db-create` satisfies every rule on this page, and what that target does is whatever the repository's `Makefile` says it does. The control at that point is a human reading the substituted command before it runs, and an approval nobody reads approves whatever was put in front of it.
- **Approval is per repository and store, not per run.** Once given, and for as long as the recorded `sourceFingerprint` still matches the file the template was discovered from, the create and its teardown run again without asking. A change to that file invalidates the approval; a change elsewhere in the repository does not.
- **Execution is the half this contract covers. Reading is not.** Discovery ingests free text — service names, notes, constraint descriptions, connection strings, whatever a compose file happens to say — into the context of the agent running the skill. A template contract can constrain what is *executed*. It cannot constrain what a model concludes from text it has read, or what it then does with tools this skill never handed it. **Nothing here is a general defence against indirect prompt injection**, which is the hazard the audit finding names.
- **Two limits declared elsewhere carry over unchanged.** The base-stack port exclusion is caller-supplied and caller-defeatable: the helpers parse no JSON, so nothing can check a passed port against the manifest it came from, and a run that passes the wrong one reaps the container (`references/reaping.md`, section 9). Ownership proof by `(pid, lstart)` leaves a same-second recycle window that nothing available closes (`references/reaping.md`, section 5). Both are already stated in `README.md` under *Honest limits*.
- **None of this has been exercised against a hostile repository.** CI checks schema negatives, script behaviour, body budgets and documented rejections. The shared-state gate has never run against a production-shaped repository, and no adversarial corpus has been built for it. The rejections above are specified and reviewed; they are not battle-tested.
- **This document predicts nothing about what a scanner will conclude.** It states the model and the residual so that both can be checked against the code. Whether any particular finding clears is not something a document can promise, and claiming otherwise would be exactly the overclaim this project treats as worse than the warning it was written to answer.

## Reporting a vulnerability

Report privately through **GitHub private security advisories** on this repository:

[Security → Advisories → Report a vulnerability](https://github.com/kevocodes/stackgraft/security/advisories/new)

That channel keeps the report private until there is a fix. Please do not open a public issue for a security report.

What makes a report actionable:

- the repository shape that reaches the behaviour — the compose file, task target or manifest, with anything private removed;
- the substituted command or launch line that actually ran;
- what happened, and what you expected the gate to do instead.

**Permissive paths are the most valuable reports.** Any route by which unknown, absent, empty or degraded data reaches an approval instead of a refusal is a security bug here, not a papercut. `CONTRIBUTING.md` already asks for those immediately, and this is the private channel for them.

**Supported versions.** The latest release only. There are no maintenance branches; a fix ships as a new release rather than a backport.
