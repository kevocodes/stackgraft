1. **RESOLVED by A5 — anchor insertion wins; a piped template with an intact anchor is ACCEPTED.** The spec's old test refused any `overlayCommand` that "pipes, wraps, redirects, or otherwise terminates the argument list"; DS24 refuses on *anchor absence*, and A5 rules DS24 right — insertion lands immediately after the `run` token, ahead of the pipe, so the labels reach the launcher and the container starts correctly labelled. `specs/topology-discovery/spec.md` now carries the anchor test: refuse when a recognised launcher exposes no anchor token, refuse an `up`-shaped template, and never match an anchor inside a quoted string. What the old test protected — never launch an unlabeled container — is unchanged. Task 1.7's fixture row is decided: piped-with-anchor is a positive fixture, and the rejected fixture is an anchorless template.
2. **RESOLVED by A7 — there is no legacy-detection mechanism, and the blind spot is the deliverable.** DS28 query 3 was an unfiltered `docker ps --all --format …`, post-filtered in `awk` against `portPolicy.ranges`; `specs/orphan-reclamation/spec.md` — "Every query is scoped to this repository" — requires the `stackgraft.repo=<hash8>` filter "in the query itself, not as a post-filter over a repository-wide listing", and greps every container-listing invocation for it. A7 settles it on the stronger ground: a container launched before instrumentation carries no label, so **nothing distinguishes it from any other container on the machine**. An unfiltered listing lists everything and identifies nothing — widening the query buys noise, not coverage. **Query 3 stays dropped and no query widens.** Task 2.4 instead names the category in the report, states that overlays launched before `stackgraft.labels` existed are invisible by construction, and prints the manual command for the user to inspect themselves. This is an **accepted coverage loss, stated loudly** — not a gap awaiting a mechanism, and not a reason to revisit the scoping requirement.
3. **RESOLVED by A6 — the carve-out widens to name the staleness reference.** `specs/portable-runtime/spec.md` carved only the lock directory and a rename; DS22's time-bounded fallback also does `: > "$destination.wait.$$"`, the `find -newer` reference, which cannot live inside `$lock` because that directory belongs to whoever holds it. The carve-out named three writes — the lock directory, one staleness-reference file adjacent to the destination created and removed by the script and empty by construction, and the rename — while the two properties it protects are untouched: scripts parse no JSON, and the agent owns the content. Applied on task 1.4. **Superseded by A11**, raised at task 3.5 and settled before archive: the script also renames the lock directory to a transient adjacent name while reclaiming it, so the count is four and that name is stated rather than read in as the mechanism of "remove".
4. **RESOLVED at task 3.3 — `manifest-contract` wins, and this change renamed onto it.** The collision was between this change's own manifest capability directory and merged `portable-multi-stack`'s `specs/manifest-contract/`, with `openspec/specs/` still only a `.gitkeep`, so neither was baseline and either name could have won. `portable-multi-stack` declares the capability *New* under that name and created the directory; this change's own spec header already called itself a *Modified* capability of it, so renaming here is the rename that costs nothing.
