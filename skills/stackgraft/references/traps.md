# Overlay traps

Each of these has been hit for real. Check them every run — they fail silently or report a false green.

## Ports

- **A port free in `lsof` is not a port available.** The user's own dev servers are not always running when you look. Treat `portPolicy.reserved` as absolute and ask before binding anything outside the allowed range.
- **Never kill a process without proving it is yours.** `lsof -a -p <pid> -d cwd -Fn` prints its working directory — that is what distinguishes your overlay from the user's work. Assuming a background server died and relaunching leaves squatters holding ports.
- **Use `--strictPort` (or the equivalent) on dev servers.** Silent fallback to the next port makes the manifest lie and the user's browser hit the wrong build.

## Ownership

- **A recorded pid is not a process — pids are reused.** The pid an overlay registered an hour ago may be the user's editor now, and every signal you send it lands on whatever holds the number today. Record `ps -o lstart= -p <pid>` beside the pid at registration and compare it as an exact string before acting; a mismatch means the pid was recycled and the process is not yours. Never parse or normalise the two strings — the same `ps` on the same host produced both, so equality is the only operation that means anything, and BSD and procps disagreeing on the format is irrelevant until you try to read it. Where `ps` has no `lstart` at all, as busybox does, the record says so explicitly and that overlay is report-only for good: an empty string recorded twice would compare equal to itself and manufacture a proof out of two absences. Procedure in `references/reaping.md`.
- **The working-directory proof has no referent once the worktree is gone — and it fails toward the dangerous side.** The check above under Ports distinguishes your overlay from the user's work by reading the process's cwd and comparing it against the worktree. That comparison is sound only while the worktree exists. Delete the worktree and there is nothing left to compare against, so the check cannot return *not yours*; it returns *unknown*, and unknown read as a pass is exactly how a run signals a stranger. The orphan case is the case the check was needed for, and it is the one case it cannot answer, so it is supplemented rather than trusted: composite identity decides, and no record means refuse.
- **`/tmp` and `/private/tmp` are the same directory and not the same string.** A worktree stored as `/private/tmp/wt` after `pwd -P` can be reported back as `/tmp/wt`, and a plain string comparison then reads *worktree gone* for a worktree that is right there. The consequence is not a wrong report: it is stopping a live overlay of live work. Normalise **both** sides with `CDPATH= cd -- <path> && pwd -P` before comparing, compare the whole value rather than a word-split of it, and treat a path that cannot be normalised as unproven rather than as absent. Symlinked spellings are the common case on macOS, so this fires on ordinary setups and not on exotic ones.
- **Two worktrees rewriting one manifest lose an entry silently, and a lock alone does not fix it.** One manifest serves every checkout of a repository, and the per-worktree port offset exists precisely because concurrent worktrees are the expected case — so two runs reaching the rewrite at once is normal, not a corner. Both read the file, both merge their own `verifiedOverlays` entry into what they read, and the second write erases the first's. Serialising the writes does not help: the loss happens in the read-modify-write **window**, not in the write, and two perfectly ordered writes lose exactly as much as two racing ones. What closes it is writing through `sh scripts/with-lock.sh` with the fingerprint the file had **when you read it**, so a destination that changed underneath is refused and you re-read, re-merge and retry. A write that could not take the lock is a failed write: name the file and do not report the record as stored.
- **An overlay launched before the labels existed cannot be found, and the report saying nothing about it is the trap.** This is a *detection* gap and not only a reclamation one: an unlabelled container carries nothing that distinguishes it from any other container on the host, so no query returns it and none can be widened into returning it — an unfiltered listing lists everything and identifies nothing, while reaching a sibling repository's containers on the way. The report therefore **cannot enumerate what it cannot query**, and a report that quietly listed the labelled overlays alone would read as *this is what is running*, which is exactly the false green this whole file exists to catch. What you get instead is one standing line naming the category, saying the invisibility is structural, and printing the command to look by hand — printed on every run, whether or not an instance exists, because the first run after instrumentation is the one that looks broken without it. **Treat that line as the signal it is.** It is an accepted coverage loss stated out loud, not a mechanism still to come, so do not wait for a later version to close it and do not read its silence about counts as a zero. Procedure and wording in `references/reaping.md`.

## False greens

- **`/health` returning 200 proves nothing about the overlay.** Header gating, CORS, auth, and tenant checks all sit above the health route. Verify a real endpoint with the real headers and read the response headers back.
- **A blocked cross-origin request still answers 200 on the server.** The browser reports only "Failed to fetch". Always inspect for the echoed allow-origin header, not just the status.
- **Widened is not opened.** After adding an origin or host to an allowlist, confirm an *unlisted* value is still rejected. Otherwise you cannot tell a widened allowlist from a disabled one.

## Wiring

- **A peer URL that is right for one overlay is wrong for the other.** `http://search-indexer:8090` resolves inside a compose network but not from the host; `localhost:<published port>` resolves from the host but points a *container* at itself. Pick per overlay, per `references/discovery.md` section 4 — never copy one form to the other kind of overlay.
- **A shared/common edit does not reach every service.** Only those whose build context includes that tree. Read the Dockerfile per service and record the answer once, in the shared entry's `consumers` list — a per-service copy of the same fact drifts out of sync and then lies.
- **Co-overlaid peers must point at each other**, not at the base stack. Rewrite those URLs to the overlay ports, or you will test the old code and believe it passed.

## Shared state

- **An all-empty classification asserted by a human is the shape of a disarmed gate.** Every pair recorded `mutates: false` and `competes: false` on `method: "user-asserted"`, beside `competesOn: []` is not a clean repository — it is what one lazy pass looks like after it told the gate what the gate wanted to hear. `[]` means *checked and none*; absent means *unknown*. Spot-check one such service against its source before trusting the set.
- **One root `stateReview` beside `backingStores: {}` disarms the gate for every service at once.** The all-empty classification above costs a lazy line per service; this costs a single record, and it is the record the schema itself describes as disarming the gate for the whole repository. It is also the easiest to write by accident, because the pass most likely to leave `backingStores` empty is the degraded one — a resolver that was down, a static parse standing in for it. Check it against the manifest, in this order: is `backingStores` an empty map rather than one nobody filled; does the record carry `confidence: "declared"` and a `method` stronger than `user-asserted`, which is one human's word about an entire repository; does some `sources[]` entry `cover` `backingStores`, does that entry's stored fingerprint still match the file today, and was that entry itself obtained by a resolver that actually ran — a covering source marked `inferred`, or still carrying a `resolverStatus`, caps the record at what it was read from, however `declared` the record calls itself. Any one of those failing means the record is not a verdict and every pair is undetermined. Then try to falsify the claim itself — one `depends_on:` naming a database, one connection string in `.env.example`, one client the code constructs, and the repository was never storeless.
- **A writer pointed at the base namespace passes every check and corrupts anyway.** Confirm the overlay's env actually names the isolated database, vhost, or prefix. An `isolation.command` that ran successfully proves the namespace exists, not that the overlay is using it. `references/discovery.md` section 6 sets `isolation.env` as a launch step; this is the check that it reached the process, which matters most for a container-run overlay, where an exported variable never crosses into the container at all.
- **The diff now selects the gate's subject, and a diff under-reports by construction — so it is safety-load-bearing rather than a convenience.** A store reached only at runtime, a connection string read from the environment, an entrypoint that migrates: none of them appears in a diff, and each is a pair the diff would have relieved for free. That is why a pair leaves the subject only on a record for exactly that pair and never on the diff alone, and why absence of a record is undetermined, which refuses. Check it against the run's own report: the derived count, every removed pair with the record that removed it, and the gated count beside the derived one — a run that prints one count has narrowed something it cannot show you.
- **A migration in the diff outranks whatever the manifest claims.** If the worktree touches a migrations directory, or the launch command runs one, treat the pair as isolate-or-refuse no matter what its determinacy record says. Migrations are the one write that damages every other consumer at once.
- **Refusing is a result, not a failure.** When the verdict is REFUSE, report it and stop. Working around a refusal by hand — creating the database yourself, reusing the shared one "just this once" — is exactly the path the gate exists to close.

## Environment

- **Never place a worktree in `/tmp` or `/var/tmp`.** Both trees are reaped on a schedule no run controls, so a worktree can vanish mid-session and take uncommitted work with it. Use `<repo-parent>/<repo-name>-worktrees/<name>` or a path inside the repo's ignored area.
- **Clone dependency trees instead of reinstalling.** On APFS, `cp -Rc <base>/node_modules <worktree>/node_modules` is a clonefile: near-instant, near-zero real disk, and each server keeps its own pre-bundle cache. Symlinking breaks that cache; reinstalling wastes minutes.
- **zsh does not word-split unquoted variables.** `for s in "catalog 8080"; do set -- $s` leaves `$2` empty and produces a URL like `localhost:/health`, which reads as a service failure. Use arrays or literals.
- **`assets/manifest.example.json` is illustrative, not factual.** It shows two services of a large compose backend, one non-runnable shared tree, and a non-dockerized dev server; a real manifest lists every runnable unit. Its ports, paths, and commands are examples — discover them against the real files instead of copying them, or the manifest lies from the first run.
- **A config dump prints secrets — unless you disable interpolation.** `docker compose config` expands every variable, so it leaks the whole `.env`; being permission-blocked for that is correct. `docker compose config --no-interpolate` leaves variables unexpanded, which is why `references/discovery.md` recommends it as the resolver. The two are not in conflict: never dump an interpolated config, always prefer the non-interpolating form. For editing a real `.env`, still ask the user and verify by observable effect.
