# Discovery and slice refresh

Discovery is expensive; run it once per repo and refresh only what drifted.

## Discovery answers two questions, not one

- **(a) path → unit** — which changed files belong to which runnable unit.
- **(b) unit → launch, port, peers** — how to start it, where it binds, how it reaches dependencies.

Many ecosystem files answer only (a). A build-graph file describes what compiles, never what listens. Treating one as a topology source produces a manifest that is confident and wrong.

## 0. Resolve `repoRoot` — the main worktree, never this checkout

One manifest serves every worktree of a repository, keyed by the main worktree, and `{{repoRoot}}` is substituted into the base-stack commands. Read it as the checkout in use and both halves break at once: the per-repo cache is discarded on every run for a `repoRoot` mismatch, and `docker compose --project-directory {{repoRoot}}` is aimed at the overlay instead of the base stack.

**`git rev-parse --show-toplevel` is not the answer.** It returns the checkout in use, which is the linked worktree exactly when the distinction matters. Derive from `gitCommonDir` instead — take the first branch that applies:

| # | Test | `repoRoot` |
|---|------|------------|
| 1 | `gitCommonDir`'s basename is `.git` | its parent directory |
| 2 | `git config -f "$gitCommonDir/config" --get core.worktree` is set | that value, resolved against `$gitCommonDir` |
| 3 | `git rev-parse --git-dir` resolves to `gitCommonDir` itself, so this checkout *is* the main worktree | `git rev-parse --show-toplevel` |
| 4 | none of the above | there is none to derive: **stop and ask** |

Read branch 2 from the common dir's own `config` file rather than through a plain `git config` lookup: with `extensions.worktreeConfig` enabled, `core.worktree` is per-worktree, so an ordinary lookup can answer for *this* checkout. Resolve every path with `CDPATH= cd -- <path> && pwd -P` before comparing or storing it, so branch 3 compares physical paths and one stored `repoRoot` keeps matching across symlinked spellings.

**Two pins on the line that produces `gitCommonDir`.** `CDPATH=` is load-bearing here for the same reason both scripts carry it: `--git-common-dir` answers the *relative* string `.git` at the worktree top, and a first component that is neither `.` nor `..` is looked up in `CDPATH` before the current directory — so with `CDPATH` exported, `cd -- .git` can enter a different repository's git dir, and it echoes the directory it chose to stdout as well. Verified: with `CDPATH` pointing at a decoy holding a `.git`, `dash -c 'cd -- "$(git rev-parse --git-common-dir)" && pwd -P'` printed the decoy path twice — once from `cd`, once from `pwd` — while the `CDPATH= cd` form printed the real common dir once. Second pin: run it **at the worktree top**, because the answer is relative to wherever it was asked (`.git` at the top, `../.git` one directory down) and means nothing in a directory the run has since moved to.

Verified on git 2.50.1, one scratch repository per shape:

| Shape | `gitCommonDir` | Branch | `repoRoot` |
|-------|----------------|--------|------------|
| Plain repo, at the top | `<r>/.git` | 1 | `<r>` |
| Plain repo, from a subdirectory | `<r>/.git`, spelled `../.git` | 1 | `<r>` |
| Linked worktree | `<r>/.git` | 1 | `<r>`, not the worktree |
| Submodule, and a linked worktree of one | `<super>/.git/modules/<name>` | 2 | the submodule's own checkout |
| `--separate-git-dir`, from the main worktree | `<elsewhere>/repo.git` | 3 | the main worktree |
| `--separate-git-dir` or bare, from a linked worktree | `<elsewhere>/repo.git` | 4 | stop and ask |

The last row is a limit of the repository, not of this rule. `--separate-git-dir` writes a one-way link: the checkout's `.git` file points at the git dir and nothing points back, so from a linked worktree the main worktree is unrecoverable — git itself answers wrongly here, `git worktree list` reporting the *git dir* as the main worktree because it derives that path by stripping a trailing `/.git` from the common dir. A bare repository has no main worktree at all. In both cases ask for `repoRoot`; substituting this checkout is the one answer guaranteed to be wrong.

`gitCommonDir` is also the cache key's input, and it is hashed exactly the way `scripts/pick-port.sh` hashes a worktree path: `printf '%s' "$gitCommonDir" | git hash-object --stdin`, with no trailing newline. `echo` would append one and digest to something else, so two runs spelling it differently would key two manifests for one repository, each rediscovering what the other already knew.

**That digest is not the key. Its first 8 characters are, and they are what `hash8` names.** Take the digest above and cut it to its first 8 characters, lowercase hex: that eight-character value is `hash8` everywhere this skill says the word — the manifest at `<repo-basename>-<hash8>.json`, the sidecar at `<repo-basename>-<hash8>.processes.json`, and the `stackgraft.repo` label every overlay carries. **Cut it anywhere else, or not at all, and the name changes.** A run keying the whole digest — 40 characters, or 64 where the repository sets `extensions.objectFormat=sha256` — looks for a file nothing has ever written: every manifest already cached is orphaned rather than reused, every label already on a running container stops matching, and the only symptom is a rediscovery that looks like a first run. Eight characters are enough because this key separates the repositories one machine has checked out, not the world's, and a collision there costs a rediscovery rather than a wrong answer — `repoRoot` is stored in the manifest and re-checked on load, so a manifest that is not this repository's is discarded on sight.

## 1. Prefer the ecosystem's resolver over hand-parsing

Compose alone has `-f` chains, `COMPOSE_FILE`, `compose.override.yaml` auto-merge, `extends`, recursive `include`, profiles, and `!reset`/`!override` directives. Hand-parsing that is a losing game.

```sh
docker compose config --no-interpolate --format json
```

merges every file and expands short notation into canonical form. `--no-interpolate` leaves variables unexpanded, so include, extends, override, and profiles all resolve **without printing a single secret**.

**Rule:** use a resolver when it is read-only, fast, and non-interpolating. Otherwise parse statically. Otherwise ask the user once and cache the answer.

| Stack | Resolver | Read-only |
|-------|----------|-----------|
| Compose | `docker compose config --no-interpolate --format json` | yes |
| Cargo | `cargo metadata --format-version 1 --no-deps` | yes |
| Go | `go list -m -json all` | yes |
| Nx | `nx show projects --json` | yes |
| Kustomize | `kubectl kustomize <dir>` | yes |
| Gradle | `./gradlew -q projects` | **no — runs a build** |
| Bazel | `bazel query` | **no — starts a server** |
| Tilt | `tilt dump api` | **no — executes Starlark** |
| .NET Aspire | `dotnet run --publisher manifest` | **no — builds and runs the AppHost** |

**When a resolver is unavailable** — Docker not running, toolchain absent — do not fail the run. Fall back to static parse, mark those entries `confidence: "inferred"`, and say so. An inferred entry still maps paths to units; it just may not be trusted for anything that gates safety.

Record *why* it degraded in `sources[].resolverStatus`: `docker daemon not running`, `gradle absent`, `resolver refused: not read-only`. Without it the next run cannot tell a genuine absence from a tool that happened to be down, and re-decides blind. With it, a `resolverStatus` that no longer applies — Docker is up again — is the signal to re-run the resolver and lift `confidence` off `inferred`, which is the only way a degraded entry ever becomes trustworthy for the shared-state gate.

## 2. Tier the sources

Record as `sources[]` every file that defines topology, with the manifest keys it `covers`. **Every entry names at least one key.** A source covering nothing still drifts and still has its fingerprint rewritten in section 5, so the one signal that file could ever give is spent on re-deriving nothing; if you cannot name what a file is authoritative for, you have not learned enough about it to record it.

**`sources` may never be empty, including when the user supplied the topology.** An empty array makes the reuse gate vacuously true forever, and the manifest stops being a cache. So a user-answered topology is recorded as a source too — `confidence: "user"`, with `resolverStatus` saying why nothing resolved it — and it is recorded **against a real file the answer is about**:

- **Attach the answer to that file.** An unparseable Tiltfile, a compose file whose resolver refused, a build file whose unit names the user mapped by hand: point `path` at it and fingerprint it. Editing the file then re-asks the question, which is the behaviour you want. Add `revalidate: "always"` when the answer rests on more than that file's own bytes — a Tiltfile importing arbitrary Starlark is exactly that — so the question is re-put every run while the entry still carries a real fingerprint the schema accepts and a later run can compare.
- **When there is genuinely no file behind the answer, write no entry and run manifest-less instead.** A path that does not exist has no fingerprint: `scripts/fingerprint.sh` returns `-` for it, section 5 step 1 treats a computed `-` as unconditional drift and forbids storing one as though it were a hash, and section 5 step 8 drops a source whose file is gone — which takes `sources` under its one-entry minimum and discards the whole manifest on the next run. An entry deleted every run caches nothing and costs a rediscovery to find that out, so cache nothing for that repository: re-ask each run, say in the output that the topology is not cached and why, and note that `references/shared-state.md` keeps every verdict obligation in that mode — manifest-less relaxes the cache, never the gate. The case is rarer than it looks: an answer that fits no file usually means the file has not been found yet, so look once more before giving up the cache.

**Tier 1 — statically resolvable, answers both (a) and (b). Use these first.**

| Source | Gives |
|--------|-------|
| Compose family via `config --no-interpolate` | services, published ports, `depends_on`, env, build context |
| `package.json` scripts + workspace globs | dev servers and their `--port` flags |
| `Procfile`, `Procfile.dev` | process list and launch commands |
| `.env.example`, `.env.sample` | peer URLs and constraints |
| `devcontainer.json` | `forwardPorts`, `appPort`, `dockerComposeFile`, `service`, `runServices` |
| `launchSettings.json` (.NET) | `applicationUrl` per profile |
| `Makefile`, `Taskfile.yml`, `justfile` | launch commands only — never ports |

**Tier 2 — k8s-indirect. A local port exists only through a forward.**

- `skaffold.yaml` → `portForward[].localPort`. Not authoritative: auto-forward silently picks a random open port when the requested one is taken.
- kustomize and plain `Service` manifests → container ports only.
- `Tiltfile` → `k8s_resource(port_forwards=...)`. This is Starlark *code*; static extraction is a heuristic, so mark it `confidence: "inferred"`.

**Tier 3 — build graph only. Use for path → unit. Never infer a port from these.**

`go.work`, Cargo workspace `members`, `settings.gradle(.kts)`, Maven `<modules>`, Bazel, `nx.json`, `turbo.json`, `pnpm-workspace.yaml`, `lerna.json`. One useful hint: a `turbo.json` task marked `persistent: true` is a dev server — that tells you a unit is runnable, not which port it takes.

Never hash a gitignored `.env`. Read the constraint it implies and record the constraint, never the secret.

## 3. Extract per unit

Resolve from the source files, never from assumption:

- **`paths`** — the globs whose change means this unit changed. Start from `build.context` for compose services, from the package directory for workspace members.
- **`buildContext`** — that build context recorded verbatim **where the unit has one**. **Where several units declare the SAME context, that context is not any one of their `paths`, and the file that builds each one says which tree is.** A monorepo commonly points every service at one shared directory, so read as `paths` a shared context maps every change under it to every unit that shares it — measured on a repository doing exactly that: a 23-file change selected **27 units where six own the changed trees**, and the twenty-one extra would each have cost a container. The unit's own tree is the directory holding its `dockerfile`, relative to that context, because that path is what the repository already wrote down about which build is whose. **A `dockerfile` sitting at the context root is the exception that is not one**: a unit built from the shared tree's root genuinely consumes all of it, so the shared context IS its own tree and every change under it selects it — correctly, and not as an artefact. Record the shared directory as the non-runnable tree it is, with those units among its `consumers`. **Where a unit's tree comes from bind mounts, record the narrowest path that carries what the unit reads, and say what the choice cost.** A mount of a whole directory is not evidence that the unit owns all of it: a `./db` mounted for the migrations one service applies also holds the initdb seeds of three stores, and recording the wide glob puts them inside that service's `paths` — so editing another store's seed drifts this unit's `serviceFingerprint`, invalidates every determinacy record hanging off it, and selects the unit for overlay. The narrow glob risks the mirror error, missing a file the unit genuinely reads. Neither is free; the narrow one fails toward re-deriving too little and the wide one toward gating too much, so **prefer the narrow glob and name the excluded siblings in `notes`** — a reader can widen a recorded decision and cannot widen one nobody wrote down. A unit running a prebuilt image with bind mounts has no build stanza at all, which is ordinary rather than exceptional, and the honest entry omits the field: what identifies such a unit's code is `paths`, which the mounts already give, and the mounts belong in `notes` if a later reader would otherwise wonder where the tree came from. *Verbatim* governs a context that exists and never the absence of one. It is not decoration: it is what decides which shared trees actually reach this unit, so a non-runnable entry's `consumers` list is derived from it rather than guessed.
- **`runnable`** — `false` for a tree that is never launched and never takes a port (shared code, generated assets). Such an entry exists only to fan a change out to its `consumers`.
- **`consumers`** — on a non-runnable entry, every unit whose build context includes that tree. This is the single direction of truth for shared-code fan-out; do not restate it as a per-service flag that can drift out of sync.

  **Report the fan-out before launching it, and report it against what is RUNNING.** A change to a shared tree can reach most of a repository, and the developer is the one who decides whether that is worth starting. So say two numbers first: how many overlays this change needs, and how many services the base stack currently has up. It is informational and it gates nothing — the run proceeds either way.

  **The denominator is the runtime's answer, never the count of units in the topology.** A compose file that defines 45 services while 19 are up makes "26 of 45" read as a saving where "10 of 19" is the real trade, and the two can point opposite ways. Measured on a real repository: a change touching a shared tree fanned out to 25 recorded consumers, of which **10 were actually running** — the honest comparison against a second full stack, not the 25 the manifest knows about. Ask the runtime what is up; a topology entry is a definition, not a fact about this moment.

  Where a unit's own diff touches no shared tree the two numbers are usually one against many, which is the case this skill is worth using for. Where they converge, the reader can see it and choose a parallel stack instead. Neither outcome is refused here.
- **`portGroup`** — which range in `portPolicy.ranges` this unit draws from. Keep it independent of `kind`, which is descriptive only. **A `portGroup` with no matching key in `portPolicy.ranges` means stop and ask.** Never guess a range, never widen another group's range to cover it, and never fall back to "any free port": the user owns this machine's ports, and a range nobody sized for this unit is how an overlay lands on one of theirs. `ranges` is optional, so the minimal manifest reaches this case on its very first overlay — it is the normal path, not an error path.

  **The key is the unit's own name unless the repository already groups its units, and that is a derivation rather than a default. **A grouping is one the repository chose in order to group** — a compose profile, a workspace member list, a directory that holds some of the units and not others. A directory every unit sits under is not one: with a single runnable unit `services/` satisfies that trivially, and so would the repository root, so a rule that accepted it would make both branches true at once and decide nothing. **One unit has no grouping**, and its name is the key.** Inventing a category — `http`, `web`, `api` — is the same act as inventing a range, one level up: it decides which units share a budget on evidence nobody supplied, and it does it silently, because a mis-keyed unit draws from a range that looks answered. A unit's name is the one key the repository has already chosen. Where it does group them — a compose profile, a workspace, a directory every one of them sits under — key by that name instead and say which grouping it was read from; a developer who wants several units on one budget edits `ranges` and the manifest carries their answer from then on.

  **Write everything else down before asking, because the question costs once and the pass costs every time.** `portPolicy` requires only `reserved`, which is derived from the base stack's published ports and needs no one's answer; `ranges` is optional, so **a manifest carrying this whole discovery and no `ranges` is valid and is what a stopping run leaves behind.** A run that stops without writing it discards a resolver pass, every fingerprint and every classification, and the next run asks the same question again having redone all of it — which reads to a developer as a skill that cannot remember, and to this cache as a repository that is never discovered. Ask for the range of the one group that blocked, record the answer under that key, and every later run for that group finds it. **What is never cached is the answer nobody gave**: a stopping run records no `ranges` entry at all rather than a placeholder one, because a key present with a guessed value is the guess this rule exists to prevent, wearing the manifest's authority.
- **`basePort`** — the port published on the host, not the container port.
- **`peerEnv`** — the env vars holding peer URLs. **This is also where an isolated store's address is delivered, and the reason no manifest field holds that address**: a seeded copy's instance name does not exist until `provision` runs and differs per worktree, so it is a value of the run and never of the cache — while `isolation.env` belongs to the in-instance road and is shared by every service paired with that store, so it is the wrong home twice over. What the manifest records is **which variable carries it**, on the unit that reads it; what the run supplies is what `address` returned. A pair whose variable is named by no route refuses before launching, which is the rule section 6 already states — and naming it here is what lets a later run repeat this launch instead of re-deriving how it was wired. See section 4; the right value depends on where the overlay runs.
- **`overlayCommand` must be a form that survives its own verification.** **The `--rm` forms in `references/reaping.md` are not counter-examples to this**: that table demonstrates **where the ownership labels are appended** in a command, and it holds whatever the rest of the line is. Read as launch forms to copy, they land a reader on one that deadlocks at step 10. A single-unit run form the orchestrator prints commonly **attaches**: `docker compose run --rm …` holds the terminal, and step 10 then has to make a request against something the run is still blocking on. Derive the detached form where the orchestrator has one, and where the only form it offers attaches — `--rm` and `-d` are mutually exclusive in Compose, so this is reachable rather than hypothetical — background the client and **record the container, never the client's pid**: `references/reaping.md` says in as many words that the pid of a `docker compose run` client is not the container, so a record naming the client is a record that cannot prove ownership of anything. A launch whose form can be neither detached nor backgrounded is verifiable only by a second terminal, which is not a thing this skill has: record that and say so rather than reporting a launch nobody checked.
- **`verifyRequest`** — a real endpoint with real headers, and **not a host**. Its closed set is `{{port}}` alone, so there is nowhere for one to go — which is correct rather than a gap: the interface an overlay answers on is the one **this run bound it to** a moment earlier, a fact of the run and never of the cache, and a stored line carrying a literal host is stale the first time a run binds elsewhere. Record the path, the method and the headers; the run supplies where to send them. `baseStack.bindsTo` is about reaching the BASE stack and decides nothing here. If any gating exists (CORS, tenant, auth), it belongs in this command. It takes one placeholder and that is its whole closed set: `{{port}}`, the port picked this run. A request goes to a listening port, so a checkout path has no place in it; any other `{{…}}` means the line was not derived from a request that can actually be made, so re-derive it or ask — and a verification that never ran records no `verifiedOverlays` entry.
- **`overlayCommand`** — the line that launches this one unit, templated with `{{port}}`, `{{worktree}}` and `{{repoRoot}}`: exactly those three, the closed set `assets/manifest.schema.json` states for this field and for `prepareCommand`. A `{{.Something}}` token is the orchestrator's own Go template — `docker compose --format` writes them — and passes through verbatim; any other `{{…}}` means the line was not taken from the repository's run form, so re-derive it or ask instead of inventing a value. Derive it from the orchestrator's own single-unit run form (`docker compose run --rm --no-deps --publish {{port}}:<container port>`) or from the package script the repo already defines; never invent one, and never use the whole-stack `up`. A dev server's strict-port flag belongs here, since silent port fallback is what makes the manifest lie.
- **`prepareCommand`** — one-time setup the worktree needs before its first launch, e.g. cloning `node_modules` instead of reinstalling. It takes the same three placeholders as `overlayCommand`, and `{{repoRoot}}` earns its place here: the thing worth cloning usually lives in the main worktree. Omit it when the unit needs none; it is not a second launch hook.
- **`dependsOn`** — every dependency the unit reaches. Each name must resolve to a `services` or a `backingStores` entry; a name in neither is unknown and fails closed. **Required on every runnable unit**, because it is what drives the redirect of unchanged peers to the base stack, so an incomplete list is a peer the overlay never rewires. It only *adds* to the shared-state gate's pair set and cannot narrow it — per `references/shared-state.md` every runnable service is paired with every `backingStores` entry regardless — so omitting a store here does not un-gate it. An empty array means checked-and-none and must carry `stateReview` like any other classification claim. Collect it from every source, not just the orchestrator's own `depends_on`: a peer named only in `peerEnv`, a connection string in `.env.example`, or a client the code constructs is a dependency too. When you cannot prove the list is complete, say so — an unproven list is not a verified-empty one.
- **`backingStores`** — one entry per stateful dependency the base stack runs, keyed by the exact name `dependsOn` uses. **Find them by the state, never by the name — of the engine, of the image, or of the service.** The signal is structural and needs no vocabulary: a unit that mounts something it can write to which **outlives the container** holds durable state, and durable state the base stack runs is a store whatever it is called. Database, broker, cache, object store, scheduler are examples of what turns up, and reading them as the list to match against is the mistake this paragraph exists to prevent — measured twice on one real repository, a name-matching pass **missed the store 28 of 41 services depend on**, because its image is `pgvector/pgvector:pg16` and no word in that string is an engine it knew.

  **Inclusive, because it is fail-closed.** A unit that persists something the map leaves out is a pair the gate never derives, and `references/shared-state.md` is explicit that a store a service forgot to declare is exactly the store the gate exists to catch. So a candidate goes in even where nothing declares it and even where what it holds looks like output rather than state — a backup volume, a cache nobody reads back. Being in the map costs one determinacy record per pair, which says checked-and-none with evidence and removes it. Being out of the map costs the gate.

  **And an undeterminable `substrate` does not block any of this.** That field says which advice in `references/shared-state.md` applies, so where the engine cannot be established the honest value is none and no substrate-specific advice applies — the pair falls to the general road, which is a copy it must verify like any other. A store is never held out of the map for want of a label. Record `substrate`, `isolation`, `locality` and — where a generated name would ever be given to this store — `nameForm` for each. **`substrate` is the engine, and an image's name is not reliably its engine.** It selects which advice in `references/shared-state.md` applies, so a brand recorded in its place selects none: `pgvector/pgvector`, `timescale/timescaledb`, `supabase/postgres` and `ghcr.io/cloudnative-pg/postgresql` are all PostgreSQL, and only one of those four names says so. Measured on a real repository: its largest store, the one 28 of 41 services depend on, runs `pgvector/pgvector:pg16` — a pass matching engine names against image names finds no store there at all, and the PostgreSQL row of that table, the one saying `TEMPLATE` needs no active connections to the source, is the advice it then does not apply. Derive it from what the image IS — the engine its entrypoint runs, the protocol it speaks, the port it exposes — and never from the string in front of the colon.

, with `mechanism: "none"` when nothing is discoverable. **`nameForm` says which member of the name family this store's namespace grammar accepts**, read from the substrate's own grammar or its own rejection, never from the store's engine name; `references/coordination-identity.md` derives the members and states that a store recording neither is undetermined, which refuses. **`locality` is where the state actually lives and who operates it** — local to this host, managed, remote, host-native, or undetermined — **derived from the discovered address and the store's discovered lifecycle, never assumed from its name, image, or engine**: the same engine runs managed and local, so a name proves nothing about where the bytes sit. Record the fact the determination rests on in `locality.reason`; it survives into the refusal message, so a developer is told which fact was missing rather than that isolation was unavailable. Undetermined is not a permission — it is read as remote and refuses. Discover the teardown in the same pass as the create: a record carrying a `command` and no `teardownCommand` is rejected, so where no drop is discoverable the honest entry is `mechanism: "none"` rather than a namespace per branch that nothing ever removes. Inside `isolation`, `applyVia` says how the command reaches the store: `compose-exec` borrows the client from inside the running container, which is why none has to exist on the host; `host-client` needs one that does; `manual` means a human runs it. Put anything a later run would otherwise rediscover into the **store entry's own `notes`**, an array — above all *why* a mechanism is `none`, since that is the record that stops the next pass from re-deriving a mechanism that does not work. **It sits beside `isolation`, never inside it**, and the distinction is worth the words because `mechanism` is one of `isolation`'s own fields, so *why a mechanism is none* reads as a note belonging where the mechanism does. `isolation` is closed to the keys listed above and has no `notes`, so writing one there emits a manifest the schema rejects — which discards the cache and buys a full rediscovery, for a note, exactly as `baseStack` does one paragraph further down. Measured: an agent recording why four stores had no mechanism put all four inside `isolation` and lost the whole pass. **Never leave a stateful dependency out of this map.** The shared-state gate fires on the dependency, so an unmapped store is a dependency the gate must refuse rather than one it can classify. **Always emit the key, even as `{}`.** An absent map is not "no stores": it is the shape a pass that never looked leaves behind, and the gate pairs every service against this map, so an empty one runs the gate zero times — see the root `stateReview` below.
- **`verification`** — the candidate query a copy of this store will have to answer, harvested in the same pass and recorded for **the stores a surviving pair will actually ask about**. Two things follow from `discriminates` being required inside the record rather than optional beside it. **The probe runs here, at discovery, not at provision**: you cannot write the record without having issued the candidate against the base store and against an empty instance, so recording `verification` is what running that comparison means, and `references/isolation-providers.md` states the three issues and the one route it goes through. And **it is not written for every store in the map**: an empty instance per store, to establish a discriminator for a pair the gate removed at pass 3 and will never read, spends a container on an answer nothing consumes. Where a store's record is left out for that reason, say so in its `notes` — an absent record is a pair that must not reach the copy road without one, which is the fail-closed direction and not a gap. Take the store service's **`healthcheck.test` in exec form only**, exactly as the resolver reported it: an exec-form test is already an argument vector, while a `CMD-SHELL` test is shell source again and is **not** a candidate — that store falls through to the next rung rather than having its line re-written into a vector. Never assemble a candidate of your own and never convert one form into the other. The template contract in `references/shared-state.md` governs this vector unchanged, so a candidate whose program re-parses its argument is rejected here for the reason it is rejected there. Record the vector, the rung it came from, and the `sourceFingerprint` of the file it was read from — that is what expires it when the store's definition drifts. Record `discriminates` beside it: a candidate is a query only once its output has been shown to differ on an empty instance of the same image, and `references/isolation-providers.md` is where that is established and where a false answer is spent. A liveness probe records `discriminates.value: false` rather than no record at all, because *checked, and it answers the same on an empty instance* is worth keeping; a store nobody could harvest a candidate for records nothing, and refuses at verification rather than at discovery.
- **`determinacy`** — the classification pass, and it runs **every runnable unit against every entry in `backingStores`**, not merely the stores the unit declares. A store a unit forgot to declare is exactly the store the gate exists to catch, so `dependsOn` may add pairs to this pass and may never subtract one. Each pair gets one record carrying `mutates` (W) and `competes` (X), the **evidence for each**, `method`, `confidence` and that unit's `serviceFingerprint`.
  **Write a record only for a pair this pass actually examined, and omit the rest.** Omission is how partial knowledge is expressed and it is the whole point of the per-pair shape: an **omitted record** is undetermined, which refuses, and it MUST NOT be written as, or later read as, checked-and-none. Never derive one pair's record from another pair of the same unit — a unit determined to write postgres has told you nothing about its Redis channel.
  **A `false` is a claim and costs evidence like any other.** `mutates.value: false` says *checked, and none, for this store* — so the `evidence` beside it says how that was established, in words a later reader can judge. A record that can say "none for this store" is a record that can say it without looking, which is why the evidence is required rather than encouraged.
  **A degraded pass writes the degraded confidence rather than lying about what it did.** Resolver unavailable, static parse standing in: the records it writes carry `confidence: "inferred"`, the manifest stays valid, the cache survives, and `references/shared-state.md` declines to count them — the same outcome an omission reaches, at no cost to the cache.
- **`competesOn`, `migrates`, `stateReview`** — recorded in the same pass. `competesOn` holds the identity **knob** for a store this unit attaches to competitively; it does not decide X, the pair's own `competes` does. **Four things are recorded per entry, and `references/coordination-identity.md` reads three of them as its proof**, so a pass that records the value alone has recorded nothing that can re-classify anything:
  1. the **knob** itself, in `identity` — the key whose name decides whether attaching competes, never its value;
  2. **the value the base stack attaches under**, in `baseIdentity`, **read out of the base stack's own configuration rather than assumed** — the resolver output, the compose service's environment, the config file the base stack loads. Record where it was read in `source`. Where it cannot be read, record no value: unreadable is the honest state and it refuses, while a value written from expectation is a comparison against nothing;
  3. **the environment variable the service itself takes that identity from**, in `overlayIdentityEnv`, read from **the service's own** configuration — the variable it already reads its `group.id`, queue, durable or lock name from. **Never invent one, never default it from a sibling service, and never derive it from a convention**: a variable the service does not read applies nothing while looking exactly like it did. It is per service because the store's `isolation.env` is not — that map is shared by every service paired with the store;
  4. whether the launch method has a **route** that sets that variable where the overlay will read it, in `deliveryRoute`, with the fact it rests on in `reason`. Section 6 enumerates the routes that exist; a launch with none records `none`, which refuses before anything is started rather than after. Record `migrates` whenever launching the unit applies migrations — from a migrate step in the command, from an entrypoint that migrates on startup, from a framework that auto-migrates — and **scope it to the stores the entrypoint is pointed at**, `{"pointing": "recorded", "stores": [...]}`. Where you established that it migrates and could not establish where, record `{"pointing": "unknown"}`: the gate leaves **every** store of that unit undetermined, which refuses. Do not collapse that into an absent `migrates`, and do not guess a store to fill it — an unscoped migration becomes a scoped one only where the scope is evidenced. `stateReview.serviceFingerprint` is computed over that unit's own `paths` with the recipe at the end of `references/shared-state.md`. The verdict procedure is `references/shared-state.md`; discovery only supplies its inputs.
- **Report the pair set's derivation, and report it every run**: the runnable units selected, the entries in `backingStores`, and the resulting pair count. A `runnable: false` entry contributes no pairs, which is why a repository of 43 services and four stores yields **156 pairs from 39 runnable units rather than 172** — a figure that is only a usable regression baseline while the derivation behind it is stated rather than inferred. Two runs against the same commit with the same manifest state report the same three counts. A run that narrows the set reports the narrowed count **beside** the derived one, never in place of it, so a narrowing cannot be mistaken for a smaller repository.

Three entries are repo-wide rather than per unit, and are extracted in the same pass:

- **`stateReview` at the root** — one record for the whole manifest, `{at, method, confidence}`, written whenever this pass leaves `backingStores` empty. It states that discovery *looked* for stateful dependencies and found none, which is what turns an empty map from an omission into a falsifiable claim; `references/shared-state.md` writes the storeless repository's single verdict against it, and refuses everything without it. **The record is written either way, and it records what this pass actually did** — *either way* meaning `declared` or `inferred`, never empty map or populated one. A populated `backingStores` needs no root record at all; the schema requires it beside an empty map and nowhere else. `confidence` is on the same scale as every other evidence record, and `declared` belongs only to a pass that established the absence itself; a run that fell back to the degraded path in section 1 — resolver unavailable, static parse standing in for it — established nothing and writes `confidence: "inferred"`. Writing it either way is what keeps the manifest valid, because the schema requires the record beside an empty map: leaving it off emits a manifest the schema rejects, which discards the cache and buys a full rediscovery every run thereafter for a repository whose resolver happened to be down once. The refusing is the read side's job instead — `references/shared-state.md` counts only a `declared` record, so an `inferred` one reaches exactly the outcome an omission would have reached, at no cost to the cache. `method` uses the same scale as the per-service record, and `user-asserted` is the weakest of all here: a human saying the repo has no database disarms the gate for every service at once, so check it against the orchestrator's own file before writing it down — that file does not count it as a verdict at the root at all. The record also needs a source, and so does the map it speaks about: at least one `sources[]` entry must `cover` `backingStores`, in every manifest and not only a storeless one. That is what gives the record something whose drift re-derives it, and what keeps a populated map owned — a `backingStores` no source covers is the gate's own pair set with no re-derivation trigger, so a repository that gains a second store never gets it into the map and never pairs it with any service. The schema rejects a manifest without that entry. Record that source's own `confidence` while writing it: `references/shared-state.md` caps the record at the covering source's, so a source that never says how it was obtained cannot evidence an absence no matter what the record claims for itself.
- **`baseStack`** — `startCommand`, `statusCommand` and `teardownCommand` from the orchestrator's own entry points. All three take exactly one placeholder, `{{repoRoot}}`: the base stack belongs to the repository, so a worktree path or a picked port has no meaning in them, and `{{port}}` or `{{worktree}}` appearing in one is a sign the whole-stack form was copied from an overlay line. A `{{.Service}}`-style token inside a `--format` string is the orchestrator's own Go template — copy it through untouched rather than reading it as an unknown placeholder — and substituted values are quoted per section 6. Record **`bindsTo`** with them: the interface the base stack publishes on, read from the published-port spec. `127.0.0.1:8080:8080` binds loopback only; `8080:8080` binds every interface. It decides what host an overlay uses to reach a base service (section 4) and whether a probe on `localhost` says anything at all, so a wrong value produces connection-refused errors that look like a dead dependency. **Where the published specs disagree, record the most restrictive of them**, and record the disagreement on the unit whose spec differs, in that unit's own `notes`. **Not on `baseStack`**: it is closed to four keys and has no `notes`, so writing one there emits a manifest the schema rejects — which discards the cache and buys a full rediscovery, for a note. One field cannot hold two bindings and the fail-closed direction is the narrow one: a value that says loopback where the truth is wider costs a wiring that goes the long way round and works, while a value that says every interface where the truth is loopback sends an overlay at a host address that refuses it, and reads as a store that is down.

  **The selector these three commands carry is read back from the runtime, never from the file that declares it.** **Where the repository's own entry point carries no selector, the selector wins and the command is derived.** A wrapper script that relies on the compose file's `name:` states no selector at all, so taking it verbatim leaves the three commands unable to name the stack they are about — and a status command that cannot name it is the empty table two paragraphs down, which step 6 reads as a stack to start. Prefer the repository's entry point wherever it can carry the selector; where it cannot, derive the orchestrator's own form and say in `notes` which script it stands in for. A project's name is whatever the run was given — `-p`, `COMPOSE_PROJECT_NAME`, or the directory when neither is set — and a `name:` in the file is only the default among those. Derive them against the selector the base stack is **actually** running under, taken from the orchestrator's own listing, and put it in the commands literally: `{{repoRoot}}` is the only placeholder they carry and a project name is not one.

  **An empty status table is not evidence that the base stack is down.** It is evidence that the selector asked for nothing, and from inside the answer those two are identical. `SKILL.md` step 6 reads that answer and starts what is missing — so a wrong selector there does not fail, it brings up a second copy of a stack that was already running, on the ports the first one holds, which is the outcome this entire skill exists to avoid. Where the listing shows this repository's containers under some other selector, the selector is wrong: **stop and name the selectors that were seen.** Only a listing that finds this repository running nowhere is a stack to start.
- **`constraints`** — repo-wide rules that break an overlay silently rather than loudly: a CORS or host allowlist, a bound interface, a port hardcoded in source, a required header, a fixed socket path. Record `kind`, `where`, `effect` and a `remedy` for each. Read them from `.env.example`, compose env blocks, and gateway or proxy config — never hash a gitignored `.env`; record the constraint it implies instead of the secret.

## 4. Reaching the base stack from an overlay

This is where overlays fail silently, and the correct answer depends on where the overlay runs.

- **Host-run overlay** (a dev server started directly) → `localhost:<basePort>`. The base stack publishes to the host, so this works.
- **Container-run overlay** → **`localhost` is the container, not the host.** A peer URL of `localhost:<basePort>` resolves to the overlay itself and fails with connection refused. Two ways out, in order of preference:
  1. **Attach the overlay to the base stack's network and keep its DNS names.** Declare that network `external: true` in the worktree's compose file, then `http://search-indexer:8090` resolves exactly as it does for the base stack. Nothing about the URL changes.
  2. **Route to the host gateway.** `host.docker.internal` on Docker Desktop; on Linux add `--add-host=host.docker.internal:host-gateway`. Then peers become `http://host.docker.internal:<basePort>`.
  3. **Run the overlay under the base stack's own project.** Where the orchestrator groups containers by a project and puts each project on a default network, launching the overlay under the selector the base stack is already running with joins that network by construction: `docker compose --project-directory {{repoRoot}} run …` does it whenever the compose file's own `name:` is that selector, and `-p <selector>` does it when the run was given one. **Prefer this over route 1 wherever it applies**, because route 1 is an edit to a compose file this skill did not author — a thing it may never make and may only name for the developer — while this one is a property of how the run is already invoked. It carries the same DNS names as route 1 and changes nothing about a peer URL.
- **Co-overlaid peer** → that overlay's address, never the base stack's. Otherwise you exercise the old code and believe it passed.

## 4b. The change set the subject is derived from

**A worktree's change is usually uncommitted, and a comparison against its base branch does not see it.** That is the ordinary shape rather than a corner: a developer opens a worktree, edits, and runs this before committing anything — `git diff <base>...HEAD` is empty on exactly the run this skill exists for, and a subject derived from it selects no unit and produces no overlay.

So the change set is **three legs, the same three the `serviceFingerprint` recipe at the end of `references/shared-state.md` hashes, and for the same reason**: the code the overlay launches is the working tree, not the commit.

1. the committed diff against the base branch, for work already committed on this branch,
2. the staged and unstaged diff, with `--no-ext-diff --no-textconv` for the reasons that recipe gives, and
3. the untracked files, from `git -c core.quotePath=false ls-files --others --exclude-standard`.

**Untracked matters most and is the easiest to drop.** A new migrations directory is untracked by definition on the run that adds it, and it is the strongest escalation the gate has — so a change set that misses it hands the gate a unit that reads as touching no store while its entrypoint is about to rewrite one.

## 5. Refresh a drifted slice

1. Fingerprint each `sources[].path` with `sh scripts/fingerprint.sh -C <repoRoot>` and record the tool that produced them in `fingerprintTool`. **That value is a literal and this is it: `git-hash-object-no-filters`.** The schema offers it as an example and a reader is free to think any equivalent spelling will do — it will not. A stored value that is not the one in use marks **every** source drifted, because two tools' values are not comparable, so a run that spells the same tool differently buys a full rediscovery and gets no warning that a spelling is what it paid for. **`-C` is not optional.** `sources[].path` is relative to `repoRoot`, the main worktree, while the run happens in the overlay's checkout: without it a relative `compose.yaml` resolves to the *worktree's* copy, and since one manifest is shared by every checkout of the repository, worktree-local topology gets written into it and every other checkout then reads full drift. The script's own `-C` exists for exactly this, so pass it every time a source is fingerprinted — first discovery, slice refresh, and the re-fingerprint a coarse pass performs in step 3. A stored `fingerprintTool` that is not the one in use marks **every** source drifted — full rediscovery — because two tools' values are not comparable and an equality test between them is meaningless rather than reassuring. Collect the drifted ones.
   **A computed `-` is drift, always, whatever is stored.** The script emits `-` for any path it could not hash — vanished, unreadable, a directory, a name git C-quoted — so `-` is the *absence* of a fingerprint, not a value that can match one. Compared against a stored `-` it would read as unchanged and hold that entry's reuse gate open forever, which is the one outcome a fingerprint exists to prevent. So `-` never satisfies fingerprint equality, and a `-` is never written into `sources[].fingerprint` as though it were a hash: re-derive that entry's `covers` this run, and if the file is genuinely gone, drop the entry per step 8.
2. Union the drifted entries' `covers`, then **remove any token that is a strict descendant of another token already in the set**. `covers` values are dot-delimited key paths: `services`, `services.<name>`, `backingStores`, `backingStores.<name>`, `stateReview`, `baseStack`, `portPolicy`, `portPolicy.reserved`, `constraints`. **Both maps take a per-key token and for the same reason**: a repository whose stores are read from different files — one declaring the database, another the broker — has one source per store and a drift in either should re-derive that store alone, exactly as it does per service.
   **`stateReview` names the root record, and `backingStores` drags it along.** The record is a claim about that very map, so a pass that re-derived the map and kept the old record would certify an absence it never re-established: re-deriving `backingStores` re-derives the root record in the same pass, and a run that finds stores drops the record rather than leaving it beside a populated map. The token exists on its own for a source that establishes the absence directly — an orchestrator file whose service list is the evidence that nothing stateful is declared — and covering it re-derives the record alone. It does not stand in for the covering source, though: `references/shared-state.md` requires some entry to cover `backingStores` itself, because that is the map the record makes its claim about, and it reads the record as stale once that entry drifts. The schema enforces the same, so a manifest whose only source covers `stateReview` is rejected.
3. **Coarse re-derives the object; the finer source still owns its key.** Refreshing `services` re-reads every source covering any part of it, including sources that did not themselves drift — and every one of those sources is **re-fingerprinted in the same pass**, because the pass just read them and a stored hash older than the read it survived is a signal already spent. Ownership does not move with the refresh: **where a finer source covers a key inside the coarse one, the finer source is authoritative for that key's value, and the coarse source supplies only the keys no finer source covers.** In the shipped example `compose.yaml` covers `services` and `apps/storefront/package.json` covers `services.storefront`, so a `compose.yaml` drift re-derives the whole `services` object from both files while `services.storefront` keeps the package file's reading of it — the coarse pass fills in every other service. Over-refresh is cheap; under-refresh is silent staleness.
4. **Fine stays fine.** A drift in `services.storefront` re-derives that key alone. It may create, update, or delete that one key — never another.
4. **Re-derivation replaces what the pass can derive and carries forward what nothing can.** `portPolicy` is the case that makes this load-bearing: `reserved` is read from the topology and belongs to the refresh, while `ranges` is the answer a human gave to the one question this skill stops to ask — no file answers it, so a pass re-deriving `portPolicy` wholesale discards it and the next run asks again. That is the behaviour the stop-and-ask rule exists to prevent, arriving through the refresh door instead. **A refresh writes `portPolicy.reserved` and leaves `portPolicy.ranges` exactly as it found it**, and `covers` may name `portPolicy.reserved` so a source can own the derivable half precisely. The general rule and not the exception: a stored value no source can answer is not stale evidence, it is the only copy.

5. **A `revalidate: "always"` source is re-derived every run, fingerprint equality or not.** Its stored hash covers the entry file alone while the set of files deciding its answer is not enumerable, so an unchanged hash proves nothing about what it pulled in.
   **The criterion is that a file this manifest does not list can change the resolved topology — not that the entry file names one.** Two shapes reach it. A file that *pulls*: a compose file using `include:` or `extends:`, a Tiltfile importing arbitrary Starlark. And a file that is *merged in without being named anywhere*, which is section 1's auto-merge: `compose.override.yaml` joins because it exists, and `COMPOSE_FILE`, an `-f` chain, a profile, or a `!reset`/`!override` directive can each bring in what no listed path covers. That second shape is the one that hides a store: adding one through a new override file moves no stored fingerprint at all, so an orchestrator that merges by convention would never re-derive the map and the new store would never be paired with any service. Set `revalidate: "always"` on the entry file whenever either shape applies to it — the shipped `compose.yaml` carries it for the auto-merge reason alone.
6. **Refreshing `services.<name>` drops that service's `verifiedOverlays` record and invalidates its `acceptedRisks` entries.** Both were evidence about code that just changed: a verification proved the old entry worked, and an acceptance was granted for the old fingerprint. Neither is refreshable from the repository, which is why no source may `cover` them — a human or a real request is the only thing that writes them back.
7. Update the drifted fingerprints and `discoveredAt`. Leave every untouched entry alone.
8. If a source file disappeared, drop it and re-discover its `covers` from scratch.
9. Discard and fully rediscover any manifest whose `schemaVersion` you do not recognize. **Discard it whole, carrying no field over**, and rediscover from the repository: there is no migration path, there does not need to be — everything here is re-derivable — and its absence is the design rather than an omission. Carrying a field forward is worse than discarding it, because a value written under one version's reading is not the same claim under the next: the retired service-level `writes` array was one claim about a whole unit, and re-reading it as evidence about one pair is the amplification `schemaVersion` 3 exists to end.

## 6. Wire and verify

**Evaluate every `constraints` entry before launching anything — every run, not only the first.** Read each `effect` and decide whether this run's ports, worktree path, or host trips it; apply the `remedy` first if it does. A constraint that bites and has no remedy is a stop-and-ask, not something to launch into and then diagnose from a false green — that is the whole reason these are recorded rather than rediscovered from a failure.

**Every command this skill substitutes into is quoted before it runs.** `overlayCommand`, `prepareCommand` and the three `baseStack` commands all take `{{repoRoot}}` or `{{worktree}}` — host paths that routinely contain whitespace — while `verifyRequest` takes `{{port}}` alone, its whole set, because a request reaches a listening port and never a checkout. So a raw substitution turns `cd {{worktree}}/apps/storefront && npm run dev` into `cd /Users/dev/my repo/apps/storefront`, which hands `cd` two operands and starts the dev server somewhere else or nowhere at all. This is the same discipline `references/shared-state.md` puts on isolation templates; only the mechanism differs, because these lines are shell lines by construction, written by the repository with their own `cd` and `&&`:

- **Running as argv** — a launch command that is one program with arguments, like every isolation command — substitute each value into **its own element**, never into a joined string.
- **Running through a shell** — anything carrying shell syntax — substitute each value as **one single-quoted word**: wrap it in `'…'` and replace each embedded `'` with `'\''`. Quote the value, not the template around it, so the line reads `cd '{{worktree}}'/apps/storefront && …` and `{{worktree}}` stays one word however it is spelled.
- **Read the substituted line before running it** — the isolation contract makes the equivalent check on its argument vector, that each value landed in exactly one element. Quoting stops the word split; it does not vouch for what the repository put in the value.

`{{port}}` is an integer from `portPolicy.ranges` and needs no protection, but quoting it too costs nothing and leaves one rule instead of two.

Then start each mapped unit with a candidate port from its `portGroup` range, the worktree as working directory or build context, `prepareCommand` run once if the entry has one, and every `peerEnv` entry rewritten per section 4 — resolving a base-stack peer against `baseStack.bindsTo`, since a stack bound to `127.0.0.1` is reachable from the host and from nowhere else. **Apply every recorded `competesOn[].overlayIdentity` in the same environment**, setting the variable its `overlayIdentityEnv` names; that launch is what makes the identity real, and a pair whose identity was recorded but not applied is undetermined and refuses per step 2 of `references/shared-state.md`. **Apply every `isolation.env` the verdict rested on** in the same way: for each store whose pair that file resolved to isolation, set every entry of `backingStores[<store>].isolation.env` in the overlay's environment. That map is half of what satisfies N — a record qualifies as a mechanism by carrying a command that creates the namespace *or* an env that points the overlay at one — so a launch that runs the create and drops the env aims the overlay at the base namespace while every signal reads green: the namespace exists, the service is up, and it is writing to the shared store. `references/traps.md` lists that outcome as something to confirm by hand; it is a step here.

**Insert the overlay label set in that same launch**, for every container-kind unit. `references/reaping.md` carries the five labels, the `stackgraft.labels` version constant, and the anchor rule; the values are quoted by the rule above, since one of them is a worktree path. Two things about it are not stylistic. It is **inserted at the anchor** inside the template — the `run` or `create` token following the launcher, ahead of the service operand — never appended, because a label appended after the operand becomes the container's COMMAND, and the shipped example's own `overlayCommand` ends at exactly that operand. And a container-kind template exposing **no** anchor is **refused, never launched bare**: an unlabelled container cannot be reclaimed, so it holds its port past the life of its worktree and the next run reads a request that landed on the squatter as a pass. That refusal enforces a rule section 3 already states — the whole-stack `up` form is not an `overlayCommand` — and its remedy is the single-unit run form section 3 would have produced anyway.

**Both of those are environment channels, and a container is a different environment.** An `export` in the calling shell reaches the `docker compose run` CLI and stops there — Compose builds the container's environment from the compose file, so an exported variable crosses only where that file names it (`environment: [VAR]` with no value forwards it from the calling environment, `${VAR}` interpolates it, an `env_file` loads it) or where the run form itself passes `-e VAR=…`. `overlayCommand` cannot be given an **environment** flag at substitution time: its placeholder set is closed to three, and appending a `-e VAR=…` the repository never wrote would be inventing a run form. **Read that as the narrow rule it is.** The label insertion above is the one named exception, and it is not the same act: it adds no value the repository has to have written, it lands at the template's anchor rather than at its end, and the resulting command equals the original with only the label elements added. Its reason is that the alternative is worse than a re-invented run form — an unlabelled container is unreapable and invisible to every later run, so where there is no anchor the launch is refused rather than run bare. An environment flag has no such forcing reason, which is why it stays forbidden here. So the launch carries the variable by a route that already exists — the worktree's own compose file, the same file section 4 has declaring the base network `external: true`, is where to name it — while a host-run overlay inherits it directly, the shell and the process being one environment there. **Where no available route carries the variable, do not launch that pair: it is undetermined and refuses.** An `isolation.env` that never reached the process leaves N unsatisfied exactly as an unapplied `overlayIdentity` leaves X undetermined, and both land on step 1 of `references/shared-state.md`.

**Where no route carries the variable, the pair refuses — and the refusal names the one line that would open it.** A compose file that writes `DATABASE_URL: postgres://…` as a literal has no channel at all: nothing forwards from the calling environment, `overlayCommand` may not be given a flag the repository never wrote, and **this skill does not edit a file it did not author** — that prohibition is general and is not scoped to the section it appears in. That is the correct outcome and not a gap: launching anyway points the overlay at the base store, which is the contamination the whole gate exists to stop.

It is a poor outcome to leave unexplained, though, because the shape is ordinary — a compose repository that hardcodes its own connection string is most of them. So the refusal **states the change and whose it is**: naming the variable in the unit's `environment:` with no value forwards it, or writing it as `${DATABASE_URL}` interpolates it, and either one is a line in the developer's own file that they make, review and commit. Name it, show it, and stop. Do not write it, do not stage it, and do not offer to — the generated lifecycle family is offered because nothing in the repository claims that ground, and a compose file somebody wrote is the opposite case.

**A seeded copy is provisioned with the launch and never before it.** The verdict at step 7 decides that a pair needs one; making it belongs to the step that uses it, so a run that stops between them — at the port question, most often — leaves no copy of the developer's data behind for a launch that never happened. A stop is cheap only if nothing expensive was done in advance of it.

Launch with `overlayCommand`, substituting `{{port}}`, `{{worktree}}` and `{{repoRoot}}`. Bind strictly: a candidate is not a guarantee, and a strict-port failure is the only authoritative signal that the port was taken. Then run `verifyRequest` and record the result in `verifiedOverlays`.
